# P30 — Harness, Loop and Graph Engineering in Astra 6

## Purpose

Execute long development tasks with controlled context, bounded verification cycles, explicit dependencies, continuous project updates and lower total consumption per accepted delivery.

Three perspectives become operational controls:

- **Harness:** what the agent sees, can access, run and change;
- **Loop:** how it acts, verifies, fixes and decides to stop;
- **Graph:** which step comes next, which dependencies exist and where human decisions are required.

## Economy principle

Token efficiency does not mean omitting evidence. It means loading only necessary context, avoiding repeated reads, summarizing logs with recoverable references, keeping reusable instructions stable and measuring cost per accepted delivery.

The complete source remains available in the repository. The agent receives the index, state, task, contracts and relevant excerpts first.

## Execution order

`IDENTIFY → MAP → PLAN → EXECUTE → VERIFY → UPDATE → RESUME`

### Harness

Before acting:

1. confirm repository, branch, revision and environment;
2. locate README, AGENTS, profile, state, decisions, tasks and checkpoint;
3. load only the applicable procedure;
4. define allowed files and tools;
5. identify secrets, external effects, production and limits;
6. use structural search before opening large files;
7. record sources and context revision.

AGENTS.md should be a short index. Details remain in versioned linked documents.

### Loop

Each task follows:

`GOAL → MINIMAL ACTION → OBSERVATION → VERIFICATION → DECISION`

Rules:

- prefer one complete, verifiable attempt;
- retry up to three cycles while the task contract remains valid;
- if failure comes from requirements, context or architecture, fix the contract before retrying;
- never repeat an external effect with uncertain outcome;
- the executor cannot change its own acceptance criteria;
- use an independent reviewer for medium or high risk;
- stop on exposed secrets, regression, expanded scope, missing authorization or insufficient evidence.

### Graph

Every mission must have nodes and transitions for input, diagnosis, specification, implementation, tests, review, security, staging, release and checkpoint.

Each node records owner, dependencies, inputs, writable resources, acceptance criteria, evidence and state: `READY`, `RUNNING`, `BLOCKED`, `FAILED`, `PASSED` or `CANCELLED`.

A node starts only after its dependencies are satisfied. Parallel work is allowed only for independent fronts and must be compared with a single-agent run.

## Astra 6 context strategy

Start with the project map, not every document. Retrieve decisions and evidence only when relevant. Keep reusable instructions stable when prefix reuse is available. Do not paste complete logs when a summary with path, lines, hash and result is enough. Compact or checkpoint after meaningful milestones. Never edit state summaries to hide divergence. Use familiar tool shapes. Delegate only independent work with its own deliverable. Default to one executor; add collaborators only when measurable. Measure tokens, time, calls, rework, human intervention and acceptance.

## Continuous update

After every meaningful milestone, update project state, decisions, evidence and pending work; record changed files and checks; create or update a checkpoint; point to the next graph node; and state whether another session can resume.

Conversation history is never the only memory.

## Completion

A task ends only with the requested implementation or diagnosis, proportional verification, updated project records, recoverable evidence, residual risks and an explicit next step or final state.

## Primary metric

`total tokens + tool calls + rework + human intervention` per accepted delivery.

A shorter log is not reported as real savings without end-to-end measurement.
